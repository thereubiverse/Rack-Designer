# Self-Hosted Stack Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One `docker compose` stack and one script that take a bare server to a working, HTTPS, signed-in application — including the first admin and their first approved device.

**Architecture:** Caddy terminates TLS and routes; the Next app and a trimmed Supabase (postgres, kong, auth, rest, storage) sit behind it. Postgres is never published. Secrets are generated by the installer, never hand-written.

**Spec:** `docs/superpowers/specs/2026-08-05-self-hosted-design.md`

## Global Constraints

- **NEVER run vitest against a directory, a glob, or an empty file list.** `*.integration.test.ts` files WIPE THE LOCAL DATABASE, which holds real data. Named files only, or the full-suite form with all three `--exclude` flags.
- **NEVER touch the running local stack.** Its container is `supabase_db_network-doc-platform` on ports 54321-54326 and it holds the user's real data. Everything here is tested on a SEPARATE compose project with different ports and its own volumes.
- Typecheck with `./node_modules/.bin/tsc --noEmit`. Bare `npx tsc` is the wrong package.
- Use `command grep`, not bare `grep`. Quote globs.
- **NEVER put a real secret in a git-tracked file.** `.env` is generated by the installer and must be gitignored.
- Commit trailer: `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`
- Pin every image to an explicit version. `latest` means a `docker compose pull` can change the database engine underneath a running deployment.

Realtime, imgproxy, studio and meta are deliberately absent — see the spec. Do not add them.

- [ ] **Step 2: `Caddyfile`** — one hostname from `${APP_HOSTNAME}`, automatic TLS, and:
```
handle /auth/v1/*    -> kong:8000
handle /rest/v1/*    -> kong:8000
handle /storage/v1/* -> kong:8000
handle                -> app:3000
```
The API paths are public because the browser fetches **signed storage URLs** directly
(`<img src={avatarUrl}>`); an internal-only address breaks every avatar and floor plan. Put that
reason in a comment — it is the non-obvious part of this file.

- [ ] **Step 3: `deploy/.env.example`** listing every variable with empty values and a comment each.
  Add `deploy/.env` and `deploy/caddy_data/` to `.gitignore`, then prove it:
  `git check-ignore -v deploy/.env`.

- [ ] **Step 4: Validate** — `docker compose -f deploy/docker-compose.yml config` must parse. Commit.

### Task 2: The installer

**Files:** Create `deploy/install.sh`

The whole "single application" requirement lives here. It must be safe to re-run.

- [ ] **Step 1: Generate secrets.** A random `POSTGRES_PASSWORD` and `JWT_SECRET`, then the anon and
  service-role keys, which are **JWTs signed with that secret** carrying `role: anon` and
  `role: service_role`. Sign them with `node -e` using built-in `crypto` — no dependency to install.
  This is the step people get wrong by hand, and the reason the script exists.

  Write them to `deploy/.env` with `chmod 600`. **Print none of them.**

- [ ] **Step 2: Prompt for** the hostname, the first admin's email, and their name. Read the admin
  password with `read -s` so it is never echoed and never appears in shell history.

- [ ] **Step 3: Bring the stack up** and wait for postgres to accept connections before continuing —
  a fixed `sleep` is a race, so poll `pg_isready` with a timeout and fail loudly.

- [ ] **Step 4: Apply migrations** — `supabase/migrations/*.sql` in filename order via `psql`. They
  were written and verified in exactly that order.

- [ ] **Step 5: Create the first admin.** Insert the `members` row with `role = 'admin'`, then create
  the auth user through GoTrue's admin API with the password from Step 2.

- [ ] **Step 6: THE BREAK-GLASS STEP — approve their first device.**

  Without this the installation is unusable. Trusted devices gate every route; approving a device
  needs an emailed code; `/users`, where an admin could approve one manually, sits behind the same
  gate. On a fresh server with email not yet proven, nobody can get in at all.

  So the installer mints a device token itself, stores its SHA-256 as an **approved** row, and prints
  the raw token **once** with instructions to set it as the `ndp_device` cookie — or, simpler and
  what the script should do by default, writes it to `deploy/first-device-token.txt` (mode 600) and
  tells the operator to delete that file once signed in.

  Print a plain warning that this bypasses the emailed-code path by design, exists for bootstrap, and
  should be revoked from `/profile` once a normal device is approved.

- [ ] **Step 7: Summarise** — the URL, the admin email, and the three things still to configure
  (SMTP, OAuth, Twilio). No secrets in the output.

- [ ] **Step 8:** `bash -n deploy/install.sh` and `shellcheck` if available. Commit.

### Task 3: Backups

**Files:** Create `deploy/backup.sh`, `deploy/restore.sh`

- [ ] `backup.sh`: `pg_dump` plus a tar of the storage volume, into a timestamped directory, with a
  retention sweep. `restore.sh`: the inverse, refusing to run unless given an explicit
  `--yes-overwrite` flag, because restoring destroys what is there.
- [ ] Both must state in their header that **a backup that has never been restored is a hope, not a
  backup** — and the doc must tell the operator to test one.
- [ ] `bash -n` both. Commit.

### Task 5: Prove the whole install on a throwaway stack

**Files:** none — evidence. Run by the controller.

**This must not touch the running local stack.** Use a distinct compose project name and ports.

- [ ] **Step 1:** Run `install.sh` against the throwaway, with a hostname of `localhost` and TLS
  disabled in Caddy for the test (real certificates need a real domain).
- [ ] **Step 2:** Confirm the stack comes up, migrations applied through `0031`, and the admin row
  and approved device exist.
- [ ] **Step 3:** Set the printed device cookie and sign in as the admin. Reach the dashboard.
- [ ] **Step 4:** Confirm from outside the compose network that **postgres is unreachable** and that
  `/rest/v1/clients` with the generated anon key is refused.
- [ ] **Step 5:** Point the grants guard at the throwaway container and confirm it passes there too.
- [ ] **Step 6:** Run `backup.sh`, then `restore.sh` into the same stack, and confirm the data
  survives — testing the restore, not just the dump.
- [ ] **Step 7:** Tear the throwaway down, remove its volumes, and confirm the real local stack is
  untouched: same ports, same data counts as before.
